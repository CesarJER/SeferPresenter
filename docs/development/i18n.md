# Interface internationalization

SeferPresenter supports Spanish (`es`), English (`en`), French (`fr`) and Hebrew
(`he`). Use the globe selector to change the interface language. UI language is
independent of the presentation, biblical corpus, transliteration and spoken
language accepted by Voice Scripture. Changing UI language does not translate
content or change the speech recognizer.

The initial Spanish interface is the authoritative migration source. English is
the reference catalog for future development. New English, French and Hebrew
translations are **machine drafts**, not linguistically approved translations.
Review English against Spanish before using it as the source for further machine
translation. Privacy and consent wording requires particular editorial attention.
The operator's published legal Markdown is never translated by this system.

## Runtime and configuration

`src/i18n/runtime.ts` owns the browser instance and the Vite JSON loaders.
`UiLocaleProvider` initializes it at each of the five entry points, and also wraps
the Audience legal page. `useUiTranslation(namespace)` subscribes components;
`translate(key, SpanishFallback, values)` resolves messages in components and
helpers. Do not evaluate a translated string once in a module-level constant:
use a function or a getter so a language change updates it.

Language priority is:

1. Valid preference for this interface in local storage.
2. Valid public server default.
3. Spanish.

Storage keys are `sefer.uiLocale.control`, `.presenter`, `.audience`, `.catalog`
and `.audioEditor`. Different roles do not overwrite one another. There are no
storage-event listeners, BroadcastChannel messages or WebSocket language fields.
Tabs of the same role share the saved preference for their next load; an already
open tab does not switch automatically. Disabled storage does not block use.
The browser's language is not an automatic default.

The Node server reads optional `SEFER_DATA_DIR/config/i18n.json` at startup:

```json
{
  "i18n": {
    "defaultLocale": "es",
    "supportedLocales": ["es", "en", "fr", "he"]
  }
}
```

`SEFER_I18N_CONFIG_PATH` can select another local JSON file; relative paths resolve
from the application root. No private file needs to exist. Nothing creates or
updates this configuration automatically. Only the four shipped locales are
accepted; the list must include Spanish and the default. Invalid, absent,
unreadable or oversized configuration falls back to the complete default list
with Spanish selected. Unknown fields are not returned.

`GET /api/public-config` exposes only the validated `i18n` object, without
authentication and with `Cache-Control: no-store`. Changing the file requires a
Node restart, **not a frontend rebuild**. This change does not restart services.
Configuration lookup is separate from locale resolution, so a future deployment
can supply another validated default without adding tenant state to the browser.

## Add a message or correct a translation

Catalogs live in `src/i18n/locales/<locale>/<namespace>.json`. Namespaces follow
the interfaces/features: `common`, `control`, `presenter`, `audience`, `catalog`,
`audioEditor`, `quiz`, `liveAudio` and `voiceScripture`.

1. Choose a stable semantic key. Keep keys when wording changes. Existing keys
   use component context, for example `control:PresentationList.newPresentation`.
2. Add English and Spanish entries; add French and Hebrew where available.
3. Use the module's hook and pass a useful Spanish fallback:

   ```tsx
   useUiTranslation('control');
   translate('control:saveChanges', 'Guardar cambios');
   translate('common:items', '{{count}} elementos', { count: rows.length });
   ```

4. Keep complete sentences together. Use named interpolation variables instead
   of concatenating grammar or manually adding plural suffixes. JSON v4 plural
   keys use `_one`, `_other`, and the additional categories reported by
   `Intl.PluralRules(locale)`; Hebrew also needs `_two`, Spanish/French `_many`.
   i18next's Intl formatters support numbers and dates, e.g. `{{amount, number}}`.
5. React renders translations as text. Do not put translated values into
   `dangerouslySetInnerHTML`, protocol constants, persisted presentation content,
   identifiers or filenames. Put formatting elements in React. Never pass an
   untrusted translation string to an HTML sink.
6. Run `npm run i18n:check` and the relevant tests. Update review metadata when a
   human checks a translation; do not describe a machine draft as reviewed.

To add a locale, add its catalogs, native selector label and locale allowlists
in the runtime, server configuration validator and checker. Include its plural
categories and direction. Add a loading/direction test. Do not change the
direction of scripture based on the new UI language.

## Validation and detection limits

`npm run i18n:check` runs in the existing verification job without a translation
API. It checks JSON syntax, nonempty values, Spanish completeness, interpolation,
plural forms and HTML. It warns about missing optional translations, unknown
references, unused keys and new literals. The TypeScript AST scanner identifies
JSX text, user-facing attributes, common display properties and dialog/error
setters. Warnings include source paths and lines.

`i18n/source-baseline.json` explicitly records unchanged technical diagnostics,
persisted content and shared metadata. Do not baseline new UI just to silence a
warning. Computed messages, runtime server diagnostics, arbitrary helper returns
and data-dependent text cannot all be classified statically. A clean check is
not proof that every possible dynamic message is translated. Existing server
protocol errors and low-level validation details may remain diagnostic text.

## Incremental translation

`npm run i18n:plan` writes a local pending-message report under
`tmp/i18n-translation/`. The separate manual `Prepare incremental translations`
workflow produces the same report as an artifact. Validation never translates;
normal PRs never call a translation provider or receive provider credentials.

`i18n/review-status.json` tracks context, source locale, per-language review status
and hashes. The cache includes key, English source, target locale, context and
provider/settings revision. Unchanged messages are skipped. `source` and
`reviewed` targets are protected, and unreviewed English blocks new downstream
translation. Existing French/Hebrew drafts were prepared from the English draft
and Spanish during migration; they still need editorial review. Locale-specific
plural variants must be reviewed together with their base message.

No provider, paid account or API key is configured. To integrate a trusted local
adapter, export `translateBatch(messages)` returning strings in the same order.
Set `SEFER_TRANSLATION_PROVIDER` to its module path and a stable
`SEFER_TRANSLATION_PROVIDER_ID`; change `SEFER_TRANSLATION_SETTINGS_VERSION` when
model, glossary or relevant settings change. Run:

```sh
node scripts/i18n-translate.mjs --apply
```

The adapter receives message identity, English text, target locale and context.
It must preserve placeholders and technical identifiers, and must not send
operator data. Provider output is validated before any output files are written.
Results stay under `tmp/i18n-translation/locales/`; review a diff before copying
them into official catalogs, then copy the corresponding manifest entries. Never
overwrite a reviewed target automatically. Credentials belong in Actions secrets
when a provider is deliberately configured there. The shipped workflow only
plans: it never invokes `--apply` and never commits.

Budgets are bounded by `SEFER_TRANSLATION_MAX_CHARACTERS` (default 10000) and
`SEFER_TRANSLATION_MAX_MESSAGES` (100); batching uses
`SEFER_TRANSLATION_BATCH_SIZE` (20). These are source-character/message limits,
not currency guarantees. A future provider must enforce any monetary limit
before making requests. Incremental machine translation uses English; migration
of the original Spanish interface is a separate editorial step.

## RTL, performance and offline behavior

UI locale controls document `lang` and `dir`. Logical spacing/position utilities
follow direction; navigation icons marked `data-ui-directional` mirror in RTL.
Media transport direction does not mirror automatically. Content renderers keep
explicit/content-derived direction and user values use bidirectional isolation
where necessary. Hebrew UI must be checked with Spanish scripture and the
reverse combination. Check focus, keyboard navigation, dialogs, tables, mobile
widths and text expansion; jsdom cannot prove visual layout.

Vite imports locale/namespace JSON as hashed chunks. Only requested resources are
loaded; there is no request per message. Spanish message defaults remain in code
for deterministic fallback and boot resilience. Optional feature namespaces load
when their UI mounts. Subscribed components rerender on language changes; audio,
timers and shared presentation state are not reset.

The existing Control/Audience service worker caches `/assets/` on use and excludes
`/api/`, including public configuration. Previously fetched locale chunks can be
reused offline. An unavailable startup locale falls back to Spanish; an uncached
language switch reports failure and keeps the current language. This does not
promise a first-ever visit offline, every unvisited language offline, or new
offline support for routes outside the existing PWA scopes.

See [local verification](../audits/2026-10-16/i18n-local-validation.md) for actual
bundle measurements, coverage and remaining manual checks.

## Future private overrides (design only)

Proposed layout: `SEFER_DATA_DIR/i18n/<locale>/<namespace>.json`, outside `public`.
Integrate through the existing data-directory resolver and a dedicated validated
server loader, not unrestricted static serving. No override loader, endpoint,
editor, private files or tenant management are implemented in this phase.

A future loader must allowlist locales/namespaces/keys, bound size and nesting,
reject dangerous keys/HTML, and match interpolation/plural schemas against the
official catalog. Return only validated messages for one requested namespace.
Resolution should be private selected-locale override → official selected locale
→ official Spanish. Add a validated bundle to the existing i18next instance;
avoid a second localization system. The official-only runtime has no dependency
on private overrides or a private data repository.
